# Java Projects Service
## О природе сервиса
Данный сервис управляет жизненным циклом java-проектов (комнат) — включая создание (генерацию), запуск, коллаборативные операции внутри комнаты, удаление комнаты и т. д.

Используемые технологии — Spring Web, Spring Data JPA (PostgreSQL), Spring AMQP (RabbitMQ), Spring Validation, Eclipse JDT Core (анализ кода, пока на стадии изучения), Spring Data Redis (Valkey). На очереди — реализация запуска проектов в изолируемой, контролируемой docker среде.

Аналогия с комнатой строится вокруг схожести природы ide – проекта с сервером/комнатой в мультиплеерных играх.
Примерно так, как на картинке (текущий фронтенд), может быть представлен список проектов-комнат, в которых некий пользователь admin является участником. (адрес /users/admin/projects):

Попасть в комнату можно, будучи автором проекта (главным администратором) или имея статус участника (для этого реализован механизм одноразовых invite-ссылок, а также ручное приглашение через поиск по username – тут происходит взаимодействие с auth сервисом).
Зайдя в комнату, пользователь оказывается в пространстве, где участники, коммуницируя друг с другом (в будущем в общении будут участвовать ai агенты) совместно редактируют и изменяют содержимое java проекта, который можно запустить, получая сообщения в консоль.
> Планируется реализовать все так, чтобы запущенный проект, если он имеет api, был доступен для внешнего мира через специальную систему ссылок, что по сути будет выглядеть, как хостинг. Для реализации этой идеи одной из главных задач будет создание возможности подключения сторонних библиотек к проекту, а также организация доступа к файлам будущего storage сервиса (либо же комната может иметь нечто вроде выделенного файлового пространства, обособленного от самой структуры проекта). Из категории смелых идей — генерация общедоступного фронтенда для написанного бэкенда, что сильно усилит функции прототипирования.

<img width="654" height="670" alt="image" src="https://github.com/user-attachments/assets/1d34af76-f0ce-40e0-ba0c-967cc1301d9f" />

Коллаборативное редактирование, включающее различные операции с папками и файлами, а также обилие действий, предполагающих запуск долгих, многоступенчатых процессов, означает взаимодействие одновременно с несколькими слоями, среди которых может быть база данных, кеш, дисковое пространство, сложные внешние системы (docker), другие микросервисы (через брокер сообщений) и даже другие пользователи (опрос пользователей в комнате перед выполнением какого-то важного действия).

Это требует построения сложной event-based системы, поддерживающей сложные стратегии синхронизации изменений внутри нее. Одновременно с этим она должна быть отзывчивой, дружелюбной для внешнего управления и конкурентной среды, и обеспечивающей обратную связь.

Система должна поддерживать сложные фронтенд сценарии — многоступенчатые диалоги, в реальном времени показывающие ход некоего процесса (сюда же относится консоль), голосования, коллаборацию с ai-агентами.

Для этого был разработан гибкий подход разработки сложных процессов — декларативные outbox цепочки, делающие каждый процесс отдельным внутренним сервисом, поддерживающим компенсации, контроль времени выполнения, а также внешний контроль со стороны других процессов посредством триггер - механизма. Основой для идеи стал outbox паттерн.
Процесс — это сервис, где пишется только бизнес логика, разделенная на шаги, а лежащий в основе outbox движок управляет ходом процесса за кулисами, запуская шаги в заданном пользователем порядке и с заданной им настройкой. Outbox подход предполагает database – driven управление процессом, связанное с иерархически разделенными внутренними ивентами.

Перед тем, как более подробно погрузиться в суть подхода Declarative Chains, рассмотрим текущий API, предоставляемый сервисом, а также структуру базы данных.
## API
Java Projects API – защищенная часть системы, поэтому все полученные запросы уже прошли этап аутентификации и имеют сформированный security контекст. Помимо этого, из заголовков формируется RequestContext {correlationId, renderId} – эти данные генерируются фронтендом.
> Коды ошибок на данный момент могут быть некорректны — в ближайшее время планируется большая работа над exception’s и соответствующими exception handler’s.

На данный момент API разделено на два логических блока — представим их сразу в виде названий Spring Controller’ов:

- ProjectsLifecycleController  - работа с жизненным циклом проекта — от создания до удаления. Иными словами — действия с сущностью Project
- ProjectsActionsController  - действия с сущностями внутри существующего проекта.

## Project Actions API – операции с файлами

Для начала отметим, что для файлов (file dto с контентом) поддерживается кеширование, что позволяет не обращаться к базе данных и диску при каждом обновлении контента. В совокупности с кешированием доступа к проекту практически все операции автосохранения (вызываемые на фронтенде) могут быть произведены без взаимодействия с базой данных и диском.

Если файл находится в кеше — кеш становится источником истины, то есть запись в диск происходит из кеша в рамках фонового процесса. Сейчас эта система находится на этапе тестирования, после которого я сформирую подробную схему.

Операция автосохранения (autosave) отличается от операции save тем, что последняя предполагает мгновенную, форсированную запись на диск. Она запускает асинхронную цепочку, в результате выполнения которой происходит синхронизация контента между базой данных, диском и кешем.
Автосохранение предполагает взаимодействие только с кешем, dto хранится как хэш, и обновление происходит в рамках хэш операции с полем content. Запись происходит по принципу last write – win, что достаточно для нужд проекта, рассылка ивента происходит мгновенно, с помощью сервиса Broadcast, позволяющего синхронно или асинхронно сгенерировать событие (ExternalEvent) для rabbitmq без обращения к цепочкам.

Для группировки действий, связанных с in-memory представлениями контента, такими как кеш, иерархическая система подсказок (в разработке) и т.д. создан сервис ContentStateProcessor, дающий актуальный доступ к контенту в проекте, а также набор хуков, влияющих на контент и связи между контентом (примеры хуков — onAutosave, onFileMove и т. д. — все подобные действия требуют перестройки модели контента, инвалидации кеша и т.д.).

Остальные эндпоинты для операций с файлами:

Их принцип работы схож с /saveFile – каждый имеет свою асинхронную цепочку, вносящую изменения с базу данных, диск и кеш.

Напомним, что цепочки являются способом организовать процесс в форме отдельного сервиса, поэтому внутри они имеют свои зависимости, обслуживающие шаги и позволяющие зафиксировать побочные эффекты процесса.

## Текущая схема дискового пространства
Cхема дискового пространства, используемая в микросервисах, представлена на общей странице проекта (на данный момент — readme для api gateway)

Хранение проектных данных на диске наравне с иерархически устроенными метаданными в базе данных обусловлено наличием тяжелым файловых операций при компиляции и запуске проекта. Разумнее сразу иметь готовую структуру на диске, а не загружать и собирать компоненты проекта из разных источников.

Наличие файловой структуры предполагает строгую синхронизацию между базой данных и диском. Неконсистентность бд и диска — критическая ошибка для онлайн ide.

## Схема базы данных

База данных предназначена для хранения метаданных проекта и связанных с ним сущностей (древовидная структура), а также метаданных процессов. Взаимодействие с базой данных реализовано как через стандартные jpa репозитории, так и через низкоуровневый jdbc template – он используется для сложных sql запросов, позволяющих работать с деревьями, не сталкиваясь с n+1 проблемой.

Поддерживаются оптимистичные и пессимистичные блокировки, позволяющие изменять данные сущностей, предотвращая состояние гонки в конкурентной среде.

Реализована блокировка по статусу сущности. Пример набора статусов:
``` // GENERATING - ЭТО ЗНАЧИТ, ЧТО ДОБАВЛЯЕТСЯ НОВЫЙ КОНТЕНТ

public enum DirectoryStatus {

 AVAILABLE, GENERATING, REMOVING, MIGRATING,

 // суть идеи - каждый шаг должен в начале поставить preparing флаг,
 // и только после проверок проставить либо GENERATING, REMOVING, MIGRATING

 PREPARING_FOR_GENERATING, PREPARING_FOR_REMOVAL, PREPARING_FOR_MIGRATING
}
```
Статусы добавляют еще больше гибкости при конкурентном редактировании сущности, плюс служат источником информации относительно текущего состояния сущности.
Как видно из названий статусов, они поддерживают создание intent локов.

Используя пример выше, опишем каждый шаг, а также покажем настройку цепочки, посредством которой она встраивается в систему.

> Код и шаги могут быть изменены позже

Прежде всего, цепочка — это отдельный spring бин, поэтому используем аннотацию @Service.

```
@Service
@ExternalResultType(event = ExternalEventType.JAVA_PROJECT_REMOVE_DIRECTORY)
public class DirectoryRemovalChain extends ControlledOutboxChain<DirectoryRemovalEvent> {...}
```

С помощью аннотации @ExternalResultType задается тип внешнего события, возникающего каждый раз, когда цепочка будет генерировать сообщение (ExternalEvent).

DirectoryRemovalChain наследуется от ControlledOutboxChain, являющего базой для всех цепочек в системе. Абстрактный класс содержит в себе всю логику организации жизненного цикла процесса, алгоритмы подготовки процесса, а также код, интерпретирующий проставленные пользователем аннотации. По итогу задача пользователя — настроить цепочку и прописать бизнес-логику процесса, разбив его на шаги.

Мы указываем тип внутреннего ивента, с которым будет работать процесс — DirectoryRemovalEvent – после каждого шага он будет записываться в базу данных в качестве payload в составе Outbox ивента (см. таблицу бд).

> Как видно из workflow схемы, цепочка может писать в outbox два типа ивентов — ивент цепочки (DeclarativeChainEvent), двигающий цепь вперед, и внешний ивент (ExternalEvent), который предназначен для внешней системы. Будучи прочитанным из базы данных, первый ивент попадает обратно в цепочку, а второй — во внешний брокер сообщений

При чтении из outbox таблицы система будет расшифровывать payload, конвертируя его обратно в DirectoryRemovalEvent. Конвертация происходит за счет того, что каждая цепочка при старте приложения регистрирует привязанный к ней ивент (@PostConstruct), имеющий свой @EventQualifier, записываемый в бд наряду с payload. После прочтения ивент публикуется в ApplicationEventPublisher (внутренние ивенты spring), попадая в цепочку и неся в себе информацию о том, какой именно шаг должен выполниться.

Для того, чтобы механизм работал, при создании цепочки мы настраиваем для нее точку входа - @EventListener, слушающий ассоциированный с цепочкой ивент. Метод входа должен быть асинхронным, что подчеркивает изолированность  контекста для каждого из шагов.

```
@Override
@Async("chainExecutor")
@EventListener
public void catchEvent(DirectoryRemovalEvent event) {
    super.processEvent(event);
}
```

Каждый ивент обязан иметь аннотацию @EventQuailifier, чтобы система могла зарегистрировать ивент для последующих расшифровок из payload (запись и расшифровка — библиотека jackson), а также наследоваться от абстрактного DeclarativeChainEvent, задающего структуру для всех событий цепочек.

```
@EventQualifier("directory_remove")
public class DirectoryRemovalEvent extends DeclarativeChainEvent<ProjectEventFromUserContext,
 DirectoryRemovalExternalData,
 DirectoryRemovalInternalData> {
}
```

С помощью дженериков явно указываются три обязательных компонента ивента — тип внешнего контекста, тип внешнего контента и тип внутреннего контента.

```
@Getter
@Setter
public abstract class DeclarativeChainEvent <

 Context extends ExternalEventContext,
 External extends ExternalEventData,
 Internal extends InternalEventData

 > {
 private Context context;
 private String message;
 private External externalData;
 private Internal internalData;
}
```

Внешний контекст — то, что несет в себе данные о том, кто инициатор процесса и какие сущности он затрагивает, а также обязательный correlation id, связывающий все ивенты, относящиеся к одному процессу. Контекст расшифровывается в notification service, так как на его основе происходит websocket routing.

Внешние данные — данные, которые передаются во внешний мир и доступны адресату. Как правило, используются непосредственно на фронтенде.

Внутренние данные — не передаются во внешний мир, в системе нужны для следующих целей:
- Несут информацию о состоянии процесса, такую как название текущего шага (для каждого шага пользователь прописывает имя), счетчик попыток, id outbox ивента, из которого было прочитано событие (для реализации callback с проставление статуса completed), а также явную пометку о том, перешел ли процесс в стадию компенсации. Такой набор позволяет, в том числе, перехватить управление над процессом, явно задав следующий шаг или явно переведя цепочку в компенсационную фазу.

- Данные, специфичные для самого процесса, которые не нужно передавать во внешний мир. Что-то вроде небольшого хранилища для информации, предназначенной, например, для выполнения следующих шагов.

> ! Описанная выше структура события продиктована специфическими условиями, сложившимися в конкретном микросервисе. Она является довольно громоздкой, пусть это и продиктовано логикой, однако в процессе выделения системы в отдельный модуль ивенты будут переработаны в первую очередь в сторону упрощения, гибкости и лаконичности.

Вернемся к рассмотрению конкретной цепочки.

Цепочка может генерировать внешние ивенты, предназначенные для публикации в брокер сообщений (автоматически — для последнего шага, вручную — через аннотацию @Message на шаге). Привязка конкретного ивента происходит через следующий метод:

```
@Override
protected ExternalEvent<? extends ExternalEventContext> bindResultingEvent() {
 return new ProjectEventFromUser();
}
```

Каждый ExternalEvent имеет свой @EventQualifier, и, будучи выразителем категории внешнего ивента (и, соответственно, узла в брокере), регистрируется сервисом ExternalQueueBridge, где явно указывается в списке пользователем. Базовая структура внешнего ивента:

```
@Getter
@Setter
@ToString
public class ExternalEvent <C extends ExternalEventContext> {
 private String message;
    private String type;
    private EventStatus status;
    @JsonIgnore
    private Long outboxParent;

    // raw json data
    private String data;

    private C context;

}
```

Так как цепочка — это одновременно процесс, и одновременно — сервис, мы можем внедрить нужные нам зависимости. Пример таких зависимостей для этого процесса:

```
@Autowired
private DirectoryRepository directoryRepository;

@Autowired
private SnapshotService snapshotService;
```

Jpa репозиторий нужен нам для crud операций в рамках директорий, snapshot сервис — для быстрых рекурсивных запросов вниз или вверх по файловом древу.

Разработка шагов происходит с явным указанием начального и конечного шагов. Каждый шаг должен содержать ссылку на следующий шаг.

В нашей цепочке первая стадия — опрос активных участников проекта, в ходе которой мы создаем триггер.

```
@OpeningStep(name = "polling")
@Next(name = "prepare_directory")
public void polling(DirectoryRemovalEvent event){...}
```

Как видно из кода, мы указываем, что это начальный шаг цепочки, даем ему имя и пишем имя следующего шага. Метод шага получает в качестве аргумента ивент цепочки — объект, связывающий весь процесс воедино.

Триггер — специальный объект, ожидающий ответа от внешней системы (в нашем случае — api запроса). Стратегия интерпретации ответа прописывается пользователем.

В данной цепочке мы используемый специальную разновидность триггера — фазовый триггер, способный проверять полученные по correlation id ответы, следуя списку созданных пользователем фаз.
Фазовый триггер поддерживает рассылку события со специальным статусом — POLLING. Получив такое сообщение, фронтенд автоматически даст сигнал (с пометкой «решение не принято») триггеру о том, что он доступен для опроса — это позволит обработать ситуации, когда пользователь получил сообщение, но по каким то причинам не отреагировал на него.
Также для триггера существует такой понятие, как onFeedStrategy – данная функция срабатывает при каждом ответе, зафиксированном триггером. Это позволяет мгновенно активировать триггер с ситуации, когда пришел ответ, делающий дальнейшее ожидании бессмысленным. В нашем примере таким ответом является сообщение, содержащее сообщение «No» и проставленный флаг decision = true.

Пример onFeedStrategy:

```
// стратегия обработки каждого из ответов
        Function<Map<String, TriggerAnswer>, Boolean> onFeedStrategy = (answers)->{
            for (TriggerAnswer answer:answers.values()){
                // демонстрация мгновенного отказа
                if (answer.isDecision() && answer.getContent().equals("No")){
                    event.setMessage("отказ в удалении директории." +
                            " Не получено одобрение других участников, просматривающих контент внутри директории");
                    event.getInternalData().setCompensationPhase(true);
                    return true;
                }
            }
            return false;
        };
```
Отметим, что во всех стратегиях и фазах кроме последней true означает, что триггер можно активировать, тем самым завершая его. False означает, что нужно ждать следующей фазы.

Если фаза последняя — true или false перестает нести какой-либо смысл.

Пример опросной фазы, срабатывающей спустя 500 мс после polling события:

```
// первая фаза - опрос
        Function<Map<String, TriggerAnswer>, Boolean> activityPollingPhaseStrategy = (answers)->{

            System.out.println("activity check phase");
            for (TriggerAnswer answer:answers.values()){
                // если обнаружен кто-то, кто не принял решение. ждем его
                if (!answer.isDecision()){
                    return false;
                }
            }
            // если все согласны, то очередь выполняет следующий шаг
            return true;
        };
```

Пример конечной фазы:

```
// конечная фаза - тут необходимо принять решение о том,
        // продолжать ли цепочку - на основании полученных ответов
        Function<Map<String, TriggerAnswer>, Boolean> finalDecisionPhaseStrategy = (answers)->{

            for (TriggerAnswer answer:answers.values()){
                if (!answer.isDecision()){
                    event.setMessage("отказ в удалении директории." +
                            " Не получено одобрение других участников," +
                            " просматривающих контент внутри директории");
                    event.getInternalData().setCompensationPhase(true);
                    return false;
                }
            }

            return true;
        };

```

Отметим, что сформированные сообщения впоследствии соответствуют тому что отображается в диалоге на фронтенде.

Сформированные фазы объединяются в специальном объекте — PhaseStrategy:

```
// для каждой фазы проставляется время срабатывания
        PhaseStrategy strategy = PhaseStrategy.constructStrategy()
                .addPhase(activityPollingPhaseStrategy, 500)
                .addPhase(finalDecisionPhaseStrategy, 5000)
                .getStrategy();
```

В финале мы собираем триггер, после чего сохраняем его с помощью родительского метода createTrigger(…):

```
PhaseTrigger phaseTrigger = PhaseTrigger.builder()
        .phaseStrategy(strategy)
        .onFeedStrategy(onFeedStrategy)
        .needPollingMessage(true)
        .correlationId(event.getContext().getCorrelationId())
        .message(event.getMessage())
        .triggerExternalData(new SimpleTriggerData(TriggerType.YES_OR_NOT, Map.of("directoryId",
                event.getExternalData().getId().toString())))
        .build();


// чтобы система увидела триггер,
// следующий шаг обязательно должен сопровождаться аннотацией waiting for
createTrigger(phaseTrigger);

```

Как видно из комментария, явное сохранение триггера обязательно. Чтобы цепочка поняла, что следующий шаг ожидает внешнего события (то есть имеет outbox статус waiting for), мы снабжаем его соответствующей аннотацией:

```
@Step(name="prepare_directory")
@Message
@Next(name = "block_directory")
@WaitingFor(time = 20)
public void prepareDirectory(DirectoryRemovalEvent event){...}
```

Таким образом, шаг будет ждать 20 секунд и, если никто не активирует должным образом триггер, произойдет компенсация. Аннотация @Message указывает, что событие после выполнения должно сгенерировать ExternalEvent – сообщение.

Дальнейшие шаги работают непосредственно с операцией удаления директории.

Они разделяют простановку в бд статусов подготовки (статус preparing_fro_removal) и блокировки (removing). Стадия блокировки предполагает проверку родительских директорий на предмет возможных параллельных операций, а также всей дочерней структуры директории — в ней также не должно быть файлов или папок, параллельно помеченных на какое-либо изменение или уже изменящихся. Таким образом реализуется паттерн intention lock.

После блокировки происходит очистка бд (отдельный шаг) и очистка диска — последний шаг:

```
@EndingStep(name = "remove_from_disk")
    public void removeFromDisk(DirectoryRemovalEvent directoryRemovalEvent){
        directoryRemovalEvent.setMessage("подчищаем диск");
        try {
            FileSystemUtils.deleteRecursively(Path.of(directoryRemovalEvent.getInternalData().getFullPath()));
        }
        catch (Exception e){
            throw new IllegalStateException("ошибка очистки диска");
        }
    }
```

Цепочка автоматически генерирует внешнее success сообщение. Диалог на фронтенде показывает пользователю, что папка успешно удалена.

Точка входа в компенсацию прописывается через переопределение метода ControlledOutboxChain:

```
@Override
    public void compensationStrategy(DirectoryRemovalEvent event) {

        // todo в идеале мы должны копировать удаляемый контент на диске в случае,
        //  если удаление диска провалилось.
        String step = event.getInternalData().getCurrentStep();

        if (step.equals("prepare_directory")
                || step.equals("block_directory")
                || step.equals("remove_from_db")){
            transaction().execute(status -> {
                Optional<Directory> directoryCheck = directoryRepository
                        .findByIdForUpdate(event.getExternalData().getId());
                if (directoryCheck.isEmpty()){
                    throw new IllegalStateException("Директории нет");

                }

                directoryCheck.get().setStatus(DirectoryStatus.AVAILABLE);
                return null;
            });
        }

    }
```

Так как компенсация получает на входе внутренний ивент цепочки, мы точно знаем — когда и при каком наборе данных произошел переход к компенсации.

## Дальнейшие мысли о цепочках

Дальнейшее развитие цепочек планируется по следующим направлениям:

- Выделение цепочек в отдельную библиотеку/фреймворк, с перестройкой некоторых систем (в частности, ивентов) и еще большей декларативностью и лаконичностью
- Добавление возможности создавать контролируемые циклы внутри цепочек, а также параллельные шаги с общей точкой взаимодействия (модификация системы триггеров)
- Организация работы с несколькими цепочками сразу (chain → subchain)
- Разработка сценариев взаимодействия с другими микросервисами (модификация системы триггеров)
- Тестирование цепочек, реализующих AI сценарии, а также попытка написания небольших агентов на базе цепочек (шаг — инструкция, шаг — инструмент и т д)
- Адаптация концепции к CDC, что сделает процессы более быстрыми за счет ухода от @Scheduled.

В любом случае, самая главная задача — выделение в отдельный модуль, так как это откроет широкие возможности для тестирования.
